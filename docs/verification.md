## v0.2.1 缩略图性能与清晰度

先前 Safari 诊断显示，缓存读取与解码之外还存在后台消息、data URL 转换和 FIFO 排队。部分缩略图过大；Safari 的 `canvas.toBlob('image/webp')` 实际回退为 PNG，原生 JPEG 编码明显更快、体积更小。这些为本机样本，不能推广为所有图片的固定耗时。

修复后，本地缓存直接只读访问，不经过后台消息、base64 或下载队列。近期缩略图按 256 MB 估算预算保留字节和解码像素，卸载卡片后保留已解码图片元素，回滚直接重新挂载。附近只预读本地资源，首次屏幕内图片优先于额外预读；缓存读取、下载、缩小和解码分开调度。旧模糊 / 过大缩略图从缓存原图重建，按 CSS 尺寸和屏幕像素密度补足像素；不透明图使用高质量 JPEG，透明图使用 PNG。已知尺寸写入元数据并在刷新时保留。

`tests/browser/thumbnail-performance.js` 使用 120 张 1024 × 1408 PNG 栅格测试原图与旧小缩略图，在 1280 × 577、2 倍屏幕像素密度下运行。12 张 408 CSS px 所需缩略图准备耗时 87 ms，输出宽度 896 px；再次访问准备为 0.1 ms，磁盘读取仍为 12 次，下载为 0 次。三档实际卡片宽度 198 / 303 / 408 px，图片均有足够的源像素。15 次滚动测试等待屏幕内图片达到所需分辨率并等待绘制帧，首次显示 P95 为 181 ms，回滚 P95 为 48 ms；回滚确认复用同一个 HTMLImageElement。透明通道、从大图返回位置均通过。该测试证明本机栅格预览行为，不代替真实 Safari 验收。

最终 30,000 张瀑布流回归仍通过：三档宽度 198 / 303 / 408 px，最多 50 张卡片，刷新锚点、大图返回、收藏筛选、缓存进度和保存 200,000 px 浏览位置正常。两个动画帧布局耗时 P95 为 35.5 ms；本次观测到的 URL 数量不是内存预算的证明，预算回收与可见资源保护由专门测试覆盖。

真实 Safari 最终测试关闭检查器后运行，在 1512 × 771 图片区域、2 倍像素密度、后台继续缓存时，三次进入 2000 / 4000 / 6000 px 的已有缓存区域，8 / 8 / 10 张屏幕内缓存图片全部显示并等待绘制帧的耗时分别为 212 / 303 / 296 ms；回滚为 82 / 6 / 33 ms，三次均复用同一 HTMLImageElement。361 CSS px 卡片使用 768 px 缩略图，超过所需 722 px，未用低分辨率预览放大替代缓存原图。已恢复测试前的尺寸与滚动位置并关闭检查器，后台缓存继续运行。

真实 Safari 样本的首访仍有超过 200 ms 的情况，不能宣称所有首访都满足 200 ms；上述为整屏而非第一张图片的耗时。旧缓存首次重新生成、图片复杂程度和后台活动会影响时间。近期回滚已避免重复磁盘读取和重新创建图片加载过程；内存资源被预算回收后，需要再次读取磁盘。全部半年图片的下载尚未完成。

80 项 Node 测试和 JavaScript 语法、资源、网站权限检查通过。8 项 SwiftPM 测试通过，覆盖原生分块与完整性校验、重复提交、导入续传、收藏与隐藏合并、损坏数据保护、空间不足分类、分页核对，以及 Retina 缩略图与透明通道。旧存储清理测试验证错误 profile、字节变化时不删除数据，成功时只移除已核对的原图；实际账号的旧存储没有清理。构建与 SwiftPM 测试使用 XcodeBuildMCP CLI，固定团队构建通过严格签名校验。

原生技术验证先使用独立测试数据，确认 App 与 Safari 扩展共享 Application Support、分块大小与 SHA-256、App 关闭后的访问。本机 64 KB / 2 MB / 8 MB 合成数据读取约 19 / 130 / 470 ms，App 关闭后 8 MB 约 515 ms；这些是本机样本，不是传输速度保证。

跨签名迁移在真实 Safari 中通过旧工具只读导出，使用每页最多 16 张的核对接口，避免一次核对整个库占用 Safari 原生消息。新 App 通过系统目录选择器读取导出目录，复制所有导出原图并逐项核对大小和 SHA-256，核对索引、收藏和隐藏 ID。App 与 Safari 均显示迁移完成，`completed === total`、`metadataVerified === true`、`oldRetained === true`。旧 IndexedDB 与导出副本均保留。关闭 App 后刷新 Safari，迁移原图仍能读取并实际显示。真实账号的图片数量、标识、签名身份及文件路径不写入公开验证记录。

本地缓存模式测试确认默认全量、暂停与继续、300 ms 可见停留、快速掠过和 overscan 不下载原图、保留来源已删除图片及收藏定位。30,000 至 30,001 张 grid 回归通过，三档宽度 198 / 303 / 408 px，最多挂载 50 张卡片，两个绘制帧布局耗时 P95 34.7 ms；刷新、过滤、大图返回和 200,000 px 查看状态保持正常。这不代表真实缩略图显示耗时。

实机验收发现 Safari 并发原生请求容易被中断，已由后台统一串行调度页面与后台请求，重试也留在同一队列。列表同步、状态更新等幂等操作允许有限重试，新状态不能越过此前尚未完成的重试；分配新暂存文件不自动重复。另一个问题是 grid 的仅按宽度缩放参数被原生层拒绝，导致读取整张原图后缩小；已修复并由 Swift 测试覆盖实际 grid 参数与非法 cover 请求。

最终 Safari 性能样本关闭检查器、暂停后台下载、App 关闭，在 2 倍像素密度下测试已有原图缓存区域。第一次生成清晰缩略图的三次整屏显示耗时为 1706 / 1589 / 3854 ms，滚回为 112 / 141 / 126 ms，均复用同一个 HTMLImageElement。原生缩略图信息与分块读取全部成功，没有读取整张原图的回退；361 CSS px 卡片的缩略图宽度为 768 px，满足所需 722 px。再次浏览相同区域为 148 / 114 / 128 ms，滚回为 37 / 50 / 58 ms。后者包含当前会话的已解码内存缓存，不能当作重新启动后的纯磁盘读取测量。

首次重建旧缩略图仍可能需要数秒，不能宣称所有已有原图的首次整屏显示都满足 200 ms。缩略图可以重建，近期回滚直接复用；解码内存被预算回收后需要再次读取。验收后恢复原来的大图、grid 尺寸与滚动位置，并继续全量缓存。迁移完成与所有官网历史图片下载完成是不同状态，后者仍在运行。

Safari 重启后的完整续传、真实磁盘耗尽、官网实际删除后的本地保留未做破坏性实机测试，由自动化测试覆盖相关规则。本次没有新提交 Describe edits 生成指令，也没有实现局域网共享。
